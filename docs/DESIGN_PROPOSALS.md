# 改変案の台帳

別セッションで受け取った2つの提案書を、**案として**登録し、実装側で検証・評価した
もの。史実の裏付けは `docs/HISTORY.md`、現行ルールの全文は `docs/GAME_RULES.md`。

## この資料の性質

- **ここに書かれていることは決定事項ではない。** 各案に「状態」を付けてある
- **元の提案書は `GAME_RULES.md`（2026-08-29 時点）を前提に書かれており、それ以降の
  実装を知らない。** 前提がずれている箇所は §1 に一覧した
- **2つの提案書は独立した裏付けではない。** どちらも `GAME_RULES.md` §16（既知の
  弱点）を読んで書かれている。あれは実装側が書いた問題リストなので、2つが同じ結論に
  達したのは同じ問題設定を渡されたからであり、**見落としがあれば一緒に増幅される**

### 状態の記号

| 記号 | 意味 |
|---|---|
| **済** | 既に実装されている（提案時点で気づかれていなかったものを含む） |
| **推** | 実装を推奨。着手待ち |
| **保** | 保留。悪くないが優先度が低いか、前提が要る |
| **否** | 採らない。理由を明記 |

## 2. 提案①〜④（両提案書に共通）

### 提案② 黒ダイヤが岩の支えになる — **済**

> 岩の支え判定に「真下が黒ダイヤ」を含める。割れた瞬間に支えが外れて岩が落ちる。
> （提案書は「最優先・実装コスト最小・効果最大」としている）

**既に動いている。** 既存の支え判定の副産物として成立していた。

```c
static uint8_t supported(uint8_t i) {
    ...
    if (!cell_dug(c, (int8_t)(r + 1))) return 1;   /* 真下が掘れていなければ支え */
```

黒ダイヤは必ず**未掘の升**に置かれる（`cell_ok` の条件）ので `dug=0` → 支えになる。
割れると `coal_hit` が `dig_sweep` を呼んで `dug=1` にするので、支えが外れる。

openMSX での実測:

```
岩(1,2) の真下(1,3) は未掘 → そこへ黒ダイヤを置く
3秒後   岩=(1,2) 状態=待機     ← 黒ダイヤが支えている
割れた状態にする (dug=1)
2.5秒後 岩=(1,3)              ← 支えが外れて落ちた
```

**残っている本当の作業は生成側にある。** 岩は「真下が土の升」に、黒ダイヤは別の
未掘升に、それぞれ独立に乱数で置かれるので、**岩が炭層の真上に乗る配置が偶然
できることは稀**で、プレイヤーにはまず見えない。→ §4.1 へ。

### 提案① 炭層の連鎖採掘 — **保**（一部済）

> 割れた黒ダイヤの升に入ったとき、同じ炭層で繋がっている割れた黒ダイヤをすべて
> 同時に採掘する。得点 200 → 400 → 800 → 1600。揺れと音を個数に応じて増幅。

**目的が現行のコンボと重なる。** 現行は「3秒以内に**速く連続で**採る」（倍率最大×8、
効果音の音程が1段2半音ずつ上昇）。提案は「**溜めて一歩で一気に**」。

**後者のほうが溜めと放出として強い**ので、採るなら**置き換え**を推す。併存させると
倍率が二重にかかる。

提案書が指摘する副次効果は正しい: 割れた黒ダイヤは通れる升なので、炭層を全部割った
時点で最大 `COAL_VEIN_MAX`(4) 升の直線通路が開通し、敵の高速道路になる。
**「1個ずつ安全に採るか、全部割ってから一気に採るか」が追加ルールなしでギャンブル
になる。**

リスク（提案書自身の指摘）: 倍率が強すぎると「全部割ってから採る」が固定の最適解に
なる。その場合は 200/300/500/800 に落とす。

### 提案④ 体温を主資源に格上げ — **一部済、一部否**

> `TEMP_TICK 15 → 10`（60秒→40秒）／つるはし +2／倒した敵が冷却アイテム（-60）

| 内訳 | 状態 | 理由 |
|---|---|---|
| つるはしを振ると発熱 | **済**。ただし **+4**（提案の倍） | 作者が段階的に +1→+2→+3→+4 と上げて決めた値。「若いステージでも1/3くらい体温が上がるようになり緊張感は出てきた」との評価 |
| `TEMP_TICK 15 → 10` | **否** | 発熱が既に +4 なので積むと壊れる。面15は振るだけで 80×4=320 で上限240を超過し、基礎が40秒になる。**提案書自身が「+2 でも面15で厳しすぎる可能性」と警告している** |
| 倒した敵が冷却アイテムを落とす | **推**（形を変えて） | §4.3 |

**狙いの評価**: 「倒す＝制限時間を買う」という論理は強い。体温が主資源になった今、
得点より時間のほうが判断として重い。ただし前のターンで**火薬を落とす**実装を
入れたので、そのままだと拾い物が増えすぎる。→ §4.3。

### 提案③ ダイナマイト＝「崩して埋める」 — **否**

> 爆風は敵を倒すと同時にその升を土に戻す（`cell_link` の四方を切る）。
> 敵の背後の通路を塞ぐ／開通した高速道路を埋め直す／埋めた升の敵は生き埋め。

**作者が明示指定した仕様の逆転にあたるため採らない。** 現行のダイナマイトは
「投げる武器・地形を掘らない・膜も壊さない・風呂も壊さない」と作者が定めたもの
（`src/bomb.c` 冒頭に仕様が書いてある）。

案としての筋は良い（唯一の「敵の通行グラフを能動的に書き換える道具」になり、
弱点6・8 が同時に解決する）が、以下の理由で保留ではなく否とする:

- 籠城の抜け穴を作る。提案書自身が「提案④とセットでないと成立しない」と認めている
- 埋め戻しには `cell_link` を**閉じる**処理が要る。現行の `link_carve` は開く一方で、
  閉じる側の再描画・敵の経路・`dug_pct` への波及が広い
- **仕様の方向を変える判断は作者のもの**であり、実装側が推す性質のものではない

作者が方針を変える場合はこの項を **推** に書き換えること。

### 提案書 1.7 の導入順について

ROM 見積（②60B → ④250B → ①250B → ③350B）は、②が実装済みで③を採らないため
そのまま使えない。§4 に実装側の優先順位を置いた。

## 3. 2つめの提案書の追加案

### 切羽圧メーター — **推**（この2文書で最も価値が高い）

> 掘った升の総数に応じて敵の透明化が早くなる。

**2つの提案書を通じて唯一の独自案で、しかも本作の核心を突いている。**

提案書自身が「掘るほど危険が増すが掘らないとクリアできない」を本作の強みとして
いるが、**現状それは実装されていない**。透明化までの時間は面番号だけで決まる:

```c
static uint16_t ghost_frames(void) {
    uint16_t d = (uint16_t)(stage - 1) * GHOST_STEP;   /* 面番号だけ */
```

`dug_n`（掘った升数）は既に持っているので、式に1項足すだけ。**数十バイト。**

| 掘った升 | 透明化まで（基礎10秒から 升×0.05秒 引く場合） |
|---|---|
| 16升（開始時） | 10.0秒 |
| 60升 | 7.8秒 |
| 120升 | 5.0秒 |

自分の行為が自分の首を締める、という環が閉じる。**提案②〜④より安く、思想に忠実。**

弱点: **見えない圧なので何が起きているか伝わらない。** HUD に出すか、透明化する敵が
増えたことで察してもらうか、設計が要る。

### 浮石（岩の周囲を掘ると不安定になる） — **否**

Dig Dug 準拠の「真下が掘れたら落ちる／真下に居る間は落ちない」は作者が繰り返し
指示して固めたルールで、プレイヤーが読める形になっている。ここに「周囲を掘ると
不安定」を足すと**「なぜ今落ちた？」が生まれる**。落石は即死なので、読めない死因は
特に痛い。

なお「浮石」は `HISTORY.md` §3 の通り**現在の岩そのものの史実名**なので、これは新機構
というより改名＋追加である。

### 局所揺れ（黒ダイヤを割ると周囲の土が掘りにくくなる） — **否**

**推奨したい行動を罰する設計。** コンボ／連鎖採掘とも正面から衝突する。速度低下は
画面に出ないので「なぜか重い」という不快さだけが残る。

### 通気（盤面に風向きを設定して敵の透明化速度を変える） — **保**

**1つめの提案書に、はるかに良い版がある**（`HISTORY.md` §5.2: 袋小路にガスが溜まり、
発破で爆発、目抜を掘れば抜ける）。`cell_link` の BFS を流用でき、史実の裏付けもある。
「盤面に風向き」は根拠が薄く画面から読めないので、採るなら §5.2 の版。

### 古い火薬（時間経過で劣化） — **否**

**作者が決めた「火薬は次の面へ持ち越す」と衝突する。** 持ち越しは「今使うか取って
おくか」の判断を生むための仕様で、劣化はそれを無効化する。

### 裏面＝深度 — **推**

両提案書が一致。`HISTORY.md` §5.3（炭層が海側へ7〜10度傾斜）に史実の裏付けがある。
空の `loop_n` に中身が入り、土の色が3面ごとに変わる既存の仕組みがそのまま深度の
表現になる。**難度パラメータをいじる理由が数字ではなく地質になる。**

| 順 | やること | 出どころ | 見積 | 状態 |
|---|---|---|---|---|
| 1 | **岩を炭層（＝炭柱）の上に置く生成ルール** | 提案②を遊べるようにする | 〜100B | 推 |
| 2 | **切羽圧**（掘った升で透明化が早まる） | 提案書2の独自案 | 〜50B | 推 |
| 3 | **梅干しドロップ**（岩で潰したとき） | 提案④＋史実 | 〜80B | 推 |
| 4 | 連鎖採掘（現行コンボと置き換え） | 提案① | 〜250B | 保 |
| 5 | 裏面＝深度 | 両提案書＋史実 | 〜150B | 保 |

### 4.1 岩を炭柱の上に置く

提案②は動いているが偶然でしか起きない。**生成側で意図的に「岩の真下に黒ダイヤ」を
作る**ことで初めて、「どの黒ダイヤをどの順で割るか」というパズルが発生する。

`HISTORY.md` §5.1 の**残柱式**がそのまま設計になり、`GAME_RULES.md` の TODO
「特殊な黒ダイヤ」の中身がここで埋まる:

> **炭柱 ＝ 耐久が高く、絵が違い、岩の下に意図的に置かれた黒ダイヤ**

支える機構は既にあるので、新規の機構は不要。

**併せて提案されている「クリア条件を全採掘から実収率○%以上へ変える」は否。**
作者が明示指定した全採掘条件と衝突し、「あと何%？」は MSX の HUD で伝えにくく、
現行の「残り何個」の明快さを失う。炭柱は**耐久が高く危険だが得点が跳ねる黒ダイヤ**
として、全採掘条件のまま成立する。

### 4.2 切羽圧

§3 の通り。`ghost_frames()` に `dug_n` の項を足す。見せ方を併せて決める。

### 4.3 梅干し — ドロップ品の整理

提案④は冷却アイテムを落とせと言い、現状は火薬を落とす。**両方を別々に足すと拾い物
の種類が増えすぎる**ので、既存の分岐に嵌める:

> **岩で潰したら梅干し（冷却）／ダイナマイトで倒したら火薬**

- 提案④の「倒す＝時間を買う」が成立する
- 「資源を使わない岩のほうが報われる」という現行の構図を維持する
- 拾い物の種類は1つしか増えない

**「塩」ではなく「梅干し」を採る理由**（`HISTORY.md` §5.5・§9）:

1. 水風呂と梅干しは同じ学芸員解説の1セットで、採るなら揃えたほうが筋が通る
2. 赤い小さな点は、既存の火薬・ダイナマイト・ボーナスと混ざらない。「塩」を白い点に
   すると、白は自機や採掘の閃きで使っているので埋もれる

## 5. 面白さの数値化（提案書 第2部） — **保**

工数が大きいので、15面の検品を本格的にやる段になってから。ただし**指摘の一部は
現時点で受け入れるべき**。

### 5.1 既存指標への批判は正しい

`GAME_RULES.md` にある「敵が1升以内に居る時間 78% → 59%」について:

> ユークリッド距離になっている。本質は `cell_link[]` であり、1升隣に居ても膜で
> 隔てられていれば敵は来られない。危険度は**通行グラフ上の最短距離**で測る

**そのとおり。** この数字は危険を過大に見ている。今後この種の測定をするときは
`cell_link` を辿った距離を使う。

### 5.2 中核となる量

**到達余裕 `T_reach`** = min over 敵i（通行グラフ上の自機までの距離[px] ÷ 敵i の速さ）

- 通行グラフは `cell_link[]` そのもの。BFS 1回（176ノード）
- 透明化中の敵は別扱い（斜めに土を抜けるのでユークリッド距離 ÷ `SPD_GHOST`）
- 湧いて点滅中（`SPAWN_WARM`）の敵は除外

**退路数 `E`** = 自機の升の隣接4方向のうち、動くと `T_reach` が増える方向の数

### 5.3 イベント定義

| イベント | 定義 | 意味 |
|---|---|---|
| ヒヤリ | `T_reach < 1.0s` に立ち下がる瞬間 | 緊張感の1単位 |
| 爽快 | ヒヤリが0.5秒以内に終わり、その間に報酬イベント（採掘・撃破）が発生 | 緊張を自分の手で解消した |
| 麻痺 | `T_reach < 1.0s` が5秒以上continuous | 危険が常態化して意味を失っている |
| 凡死 | ヒヤリが `E`=0 の状態で始まった | 詰み。判断で回避できていない |
| 退屈 | `T_reach > 3.0s` かつ報酬イベントなしが3秒以上 | 掘るだけの時間 |

緊張感 = ヒヤリ/分、爽快感 = 爽快 ÷ ヒヤリ、麻痺と凡死は減点（これがないと
「敵を増やせば指標が上がる」抜け道ができる）。**1面あたりヒヤリ3〜6回**が出発点。

**放出量** = 0.3秒窓内の（得点 ＋ 変化した升の数 ＋ 同時に鳴った効果音の種類数）の
ピーク値。爽快感は「解消したか」（率）×「どれだけ派手に解消したか」（振幅）で、
**現状は振幅がほぼ一定なのが「爽快感が足りない」の正体**という診断。

### 5.4 パズル性

定義は**貪欲な手順と最適な手順の差**。差がゼロなら考える意味がない。面15でも炭層は
4本 → 採掘順は 4! = 24通りで全探索できる。

- **順序依存度** = 24通りのクリア時間の変動係数。0.05未満なら順序に意味がない
- **貪欲差** = 最寄りの炭層を順に取るボットの成績 ÷ 最良順序の成績
- **不可逆点の数** = 岩の落下・風呂の破壊・火薬の消費の回数

**§4.1（岩を炭柱の上に置く）が効いたかどうかは、順序依存度が上がるかで判定できる。**

### 5.5 実装手順

1. **ホストビルド**。VDP/PSG を叩く部分をスタブに差し替え、gcc でヘッドレスに。
   乱数は seed 固定
2. **状態ログ**。毎フレーム 自機升／向き／体温／各敵の升と状態／`cell_link` の
   ハッシュ／得点差分／入力。1面3600フレームなので CSV で十分
3. **ボットを2つ**。貪欲（最寄りの炭層へ最短路）と順序全探索
4. **指標を Python で算出**。BFS と閾値判定
5. **openMSX の script で実機ログも取り**、ホストビルドとの一致を確認

### 5.6 限界（提案書自身の注意。重要）

- **指標は「面白さ」ではなく「面白さの必要条件の欠落」を測る道具。** ヒヤリ0回の面は
  つまらないと断言できるが、ヒヤリ5回の面が面白いとは断言できない。**否定側にだけ強い**
- **Goodhart の罠。** ヒヤリ回数を最大化しにいくと、敵を増やして通路を狭くするのが
  最適解になり理不尽なゲームができる。**目的関数ではなく合格/不合格のゲートとして使う**
- **較正には人間が要る。** 閾値（1.0秒/0.5秒/3.0秒）は実際に遊んだ申告と突き合わせる。
  申告なしでやるなら**入力ログの方向反転頻度**がパニックの代理変数になる
- **新奇性は測れない。** 「初めて岩の連鎖を見たときの驚き」は乗らない
