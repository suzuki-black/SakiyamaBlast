# 落盤で落ちる岩の順番 ── 実装指示書

`docs/ROCK_CAVEIN_ORDER.md` の相談への結論。
**「速度の単位を揃えて、隠れた時間の貸し借りを消す」**という方針。

- 対象: `src/rock.c`（`rock_collapse()` / `rock_fall_step()`）、`src/game.h`、`src/field.c`
- 概算: **120B 前後**（固定領域の空き 1412 バイト）
- **新しい規則はゼロ。定数が1つ消える**

> **先に §9 を読むこと。**
> この指示書は**面1の1ケースの実測から導いた仮説**であって、検証済みの設計ではない。
> 確かめられていない点を §9 にすべて列挙してある。

---

## 0. 診断 ── 単位がばらばらだった

実測（面1・種31254）で勝敗を決めていた量は3つ。

| 量 | 現行 |
|---|---|
| 1升落ちる | 8フレーム |
| 樋を横に渡る | 8フレーム |
| **行ごとの落下開始のずれ**（`CAVEIN_ROW_DELAY`） | **10フレーム** |

**10 だけが仲間外れ。** 落下と樋は升で数えられるのに、開始のずれだけ升で割り切れない。

```
岩1 が得た先行     +10f（行1と行3の差 × CAVEIN_ROW_DELAY 2行ぶん … 実測では20f）
岩1 が失った迂回   -8f（樋の横移動）
                   ────
                   実測の勝敗は 4フレーム差
```

**この「4フレーム」は盤面のどこにも書かれていない。**
`ROCK_CAVEIN_ORDER.md` §7 の失敗の型（盤面を見ても分からない量で勝敗が決まる）と同じ。

**対処は、新しい量を作って画面に出すことではなく、単位を揃えて量そのものを消すこと。**

---

## 1. 変更する3点

### ① `CAVEIN_ROW_DELAY` を削除する

**落盤で落ちる岩は、全部同じフレームに落ち始める。**

この定数は「上の行の岩を先に出す」ためのものだが、
**上を先行させると下の岩に追いつく。追突を防ぐどころか作っていた。**

削除すると、落下中の岩はすべて同じ速さで降りることになる。

### ② 樋の横滑りを、ちょうど1ブロックぶんの時間（8フレーム）にする

現行の `ROCK_SLIDE_SPD` 2px/frame × 8フレームがそのままなら**変更不要**。
ずれているなら 8 に揃える。

これで岩の動きが1文になる。

> **岩は常に 2px/フレームで動く。下へか、樋では横へ。**

速さは一定で、向きだけが変わる。**樋は1段ぶんの時間を食うが、高さは変わらない。**

### ③ 使った樋は「折れた板」の絵を残す

現行は普通の坑道に戻るが、**折れた板のタイルを残す。**
通行にも落下にも影響しない、ただの跡。

**2番目の岩が真っ直ぐ落ちた理由が、画面に書いてある状態になる。**

---

## 2. これで何が変わるか

### 勝敗の読み方が「歩数」になる

実測の盤面で計算し直す。両方とも45フレームで落ち始め、8フレーム/歩。

```
岩1(9,1)  (9,2)採 → (9,3)採 → (9,4)採 → (9,5)樋 → 横 → (8,6) → (8,7)
           1        2        3        4      5     6      7歩

岩0(8,3)  (8,4)採 → (8,5)   → (8,6)   → (8,7)
           1        2        3        4歩
```

**岩0 が4歩、岩1 が7歩。岩0 が3歩ぶん先に下の樋へ着く。**

結果は現行と同じだが、**理由が変わる。**

| | 現行 | 変更後 |
|---|---|---|
| 勝敗の理由 | 先行20f − 迂回8f ＝ **4フレーム差** | **経路の歩数の差**（4歩 対 7歩） |
| プレイヤーに読めるか | 読めない | **指でなぞって数えられる** |
| 負けた側が見るもの | 何もない升 | **折れた板** |

### 規則は1文で言える

> **樋までの歩数が少ないほうが勝つ。同じ列なら、下にいるほうが勝つ。**

### 「追いつく」が構造的に起きない

これは規則ではなく、①②から出てくる帰結。

> **どの岩も同じ速さで動くので、前の岩が止まらない限り、後ろの岩が追いつくことはない。**

樋で時間を失う岩はいても、**時間を得る岩はいない。**
落下中の岩どうしが競り合って接触する状況が、構造的に起きなくなる。

## 3. 岩と岩が接触する4つの場合

上の通り「追いつき」が消えるので、接触はこの4通りに限られる。
**どれも既存の規則で処理でき、新しい規則を足さない。**

### (A) 追突 ── 前の岩が止まっていた

下の岩が土や盤面の底に着いて止まり、後ろから降りてきた岩がそこへ到達する。

**規則6で、落ちてきたほうが割れる。**

- **前の車が止まって、後ろの車が追突した。** 説明が要らない
- 下の岩が止まる場所は足元を見れば分かるので、**予測もできる**
- **落盤中の接触は、ほぼ全部がこれになる**

### (B) 樋の行き先に岩がいた ── 曲がらない

既存の規則がそのまま使える。

> 曲がった先が塞がっていたら、曲がらず、そのまま真下へ落ちる

**「塞ぐもの」に岩を含めるだけ。新しい規則はゼロ。**
板は壊れ、岩は真っ直ぐ落ちる。

横から押しても岩は岩を通り抜けられないので、**押しの挙動と一致している。**

### (C) 横から入ってきた岩に当たる

樋で列を移った岩が、落下中の岩の真下に入り込む場合。
次の歩で上の岩が着地して、**規則6で落ちてきたほうが割れる。**

4つの中では唯一やや意外な形だが、
**両方とも画面に見えていて、割れるのは「落ちてきたほう」という同じ規則。**
例外を作らない。

### (D) 押して積んだ

**規則6の通り割れない。変更なし。**

そして**これが唯一の「接触を避ける手段」になる。**

```
落盤の前に岩を押して縦に並べておく
  → 上の岩は「落ちる岩」ではなく「載っている岩」になる
  → 下が落ちた後に支えを失い、遅れて降りる
```

**追突を避けながら、時間差の連鎖を自分で仕込める。**
規則を足さずに戦略が1つ増える。

## 4. 同時に落として読ませる演出

「同時だと一瞬で片付いて読めない」への対処。**どれも VRAM を触らない。**

### ① 揺れが配役を予告する

`ROCK_JIG_FRAMES` 45フレームの揺れが**全員同時に始まる。**

- **落ちる岩が一斉に震え出すので「今回は3個落ちる」が一目で分かる**
- 真下が土の岩は震えないので、**動く岩と動かない岩の区別も同時に付く**

### ② 編隊で降りるほうが目で追える

全部が同じ速さで平行に降りるので、視線が散らない。
**ばらばらに落とすほうがむしろ読みにくい。**

### ③ 採掘の表示と音だけ、岩ごとに2フレームずらす

**処理は同時のままでよい。** 表示と音だけをずらす。

同じフレームに採掘が重なると得点表示と音が潰れるので、
**岩の番号順に2フレームずつずらす。**
連鎖が 200 → 400 → 800 と階段状に聞こえるようになる。

### ④ 落盤全体が1本の連鎖になる

**盤面の岩が動いている間は連鎖の窓を開かない**ので、落盤全体が繋がる。
**最後に止まる岩が一番大きい数字を稼ぐ。** 面の締めとして収まりが良い。

## 6. 維持する仕様（変更しないこと）

| | |
|---|---|
| **「落下距離に樋の1升を数えない」** | **維持。** 数えると樋を通った岩が割れやすくなり連鎖が途切れる。高さは変わらないので理屈も通る |

| **待機中の岩に敵が触れたら押し負けて逃げる** | **維持。** 現行どおり |
| **敵は透明中も岩をすり抜けられない** | **維持。** 現行どおり |
| **真下が土の岩は落盤で動かない** | **維持。** 足元を見るだけで判定でき、押して運ぶ遊びが面の後半に残る |
| 規則1〜6 | **すべて維持。1つも変えない** |

## 7. §7 の失敗の型を踏まないことの確認

`ROCK_CAVEIN_ORDER.md` §7 で捨てた6件は、全部
**「新しい量を作って、それを画面に出そうとして失敗」**している。

今回は逆。

> **量を作らず、既にある3つの量の単位を揃えているだけ。**

- 新しい規則: **ゼロ**
- 消える定数: **1つ**（`CAVEIN_ROW_DELAY`）
- プレイヤーが覚えること: **ゼロ**

判定基準は「画面に出せるか」より
**「覚えなくても、見たまま以外のことが起きないか」**のほうが安全。

①②を入れると、**速い岩も遅い岩も存在しない**ので、
プレイヤーが規則を知らなくても裏切られない。

## 8. リスクと確認点

- **樋を通る岩が増えるほど、歩数の差が開く。**
  いまは実質1〜2個の岩しか樋に届いていないはずだが、全部同時に落とすと届く岩が増える。
  **折れた板を見つけて「取られた」と分かる**ようにしておけば納得感は保てるが、
  **樋が毎回上の岩に食われるようなら配置の見直しが要る**
- **(C) の割り込みが実際にどれくらい起きるかは未知数。**
  シミュレータで**「横から入ってきた岩に当たった回数」**を全15面で数え、
  **数回以下なら放置、多いようなら樋の配置で列を分ける方向へ振る**
- **押して介入するときだけ、歩数では読めない。**
  揺れている岩を押して列をずらすと、押している間の8フレーム前後で勝敗が変わる。
  **意図的な介入なので許容範囲**だと思うが、遊んでみて判断すること
- **落盤の途中でプレイヤーが別の岩の下を掘ると、その岩だけ出遅れる。**
  編隊から外れるので追い抜かれたり追突したりするが、
  **自分でやったことなので見えている。** 許容してよい

## 9. 【重要】この指示書で確かめられていないこと

**提案者（Claude）が計算・推論で確認できなかった箇所。**
実装前に目を通し、想定と違ったら指示書ごと疑うこと。

### 9.1 実測データは1面・1ケースしかない

判断の根拠にしたのは `ROCK_CAVEIN_ORDER.md` §4 の
**面1（種31254）で炭柱(8,6)を割った1回分のフレーム記録だけ。**

- **残り14面の盤面を見ていない**
- **同じ面でも、もう1本の炭柱を割った場合を見ていない**
- 岩が3個以上同時に落ちる場合を一度も追跡していない

§2 の「歩数で読める」は、この1ケースで成り立つことを確認しただけ。
**岩が4個以上落ちる面で同じように読めるかは未検証。**

### 9.2 「追いつきが構造的に起きない」の適用範囲

§2 の主張は、**厳密には「落下中の岩どうし」にしか成立しない。**

前提は「全員が同時に落ち始め、全員が同じ速さで動く」ことだが、次の場合は前提が崩れる。

| 前提が崩れる場面 | 扱い |
|---|---|
| 落盤の途中でプレイヤーが別の岩の下を掘る | §8 で「自分でやったことなので許容」としたが、**実際の頻度も体感も未確認** |
| 揺れている岩をプレイヤーが押す | **押している間の勝敗が歩数で読めない。** §8 に書いたが、どの程度不快かは未確認 |
| 敵が岩を押す | **まったく検討していない。** 敵も岩を押せる仕様なので、落盤中に敵が押した岩がどう振る舞うか不明 |
| 落ちた岩が樋で列を移った先に、静止した岩がいる | (B) で処理されるはずだが、**タイミングによっては (C) と区別がつかない可能性** |

**「絶対に接触しない」と書いた箇所があれば、それは落下中の岩どうしに限った話。**

### 9.3 (C)（横からの割り込み）の頻度が読めなかった

§3-(C) は4つの接触の中で**唯一やや意外な形**だが、
**どれくらい起きるか計算できなかった。**

樋を通った岩が、別の落下中の岩の真下に入り込む確率は、
樋の位置・岩の初期配置・炭柱の位置の組み合わせで決まる。
盤面を14面ぶん見ていないので推定の根拠がない。

**多発するようなら、この指示書の前提（接触は追突がほとんど）が崩れる。**

### 9.4 樋を通る岩が増えるかどうかが読めなかった

`CAVEIN_ROW_DELAY` を削除すると落ち始めが揃うので、
**樋に届く岩の数が現行より増える可能性がある。**

増えた場合に起きうること:

- **上の岩が毎回樋を食って、下の岩が一度も通れない**
- 折れた板を見れば「取られた」ことは分かるが、
  **毎回同じ岩に取られるなら樋の意味が薄くなる**
- 逆に、現行より樋の通過が減る可能性も否定できない（先行のずれが無くなるため）

**どちらに転ぶか計算できなかった。**

### 9.5 演出の効果は推測

§4 の「編隊で降りるほうが目で追える」「一斉に震えると配役が分かる」は、
**視認性についての推測であって、実測でも前例でもない。**

- 岩が5個以上同時に震えたとき、**うるさく見えないか**は分からない
- 採掘の表示を2フレームずらす案は、**岩が4個以上だと最大8フレームずれる。**
  その間に別の岩の採掘が挟まると順序が入れ替わって見える可能性がある

### 9.6 スプライトまわりを実機で確認していない

- 岩が全部同時に落ちると、**中間位置で複数の岩が同じ走査線にかかる時間が増える。**
  横8枚制限に触れないか未確認（自機1・爆弾1・岩8・敵6・かけら6 で22面使用）
- 折れた板のタイル追加が、背景タイル12枚の枠に収まるか未確認

### 9.7 結論として

**この指示書は「1ケースの実測から導いた仮説」であって、検証済みの設計ではない。**

§1 の3つの変更（`CAVEIN_ROW_DELAY` 削除・樋8フレーム・折れた板）は
**どれも小さく、戻すのも簡単**なので、まず入れて §10 を測るのが早いはず。

ただし **§9.3 と §9.4 の結果次第では、方針ごと見直しが要る。**

## 10. 実測してほしいこと

シミュレータ（ホスト側に同じゲームロジックを gcc でビルドしたもの）で、
**変更の前後を全15面で比較する。**

| 指標 | 期待 |
|---|---|
| **岩どうしが接触した回数** | 落盤中の「追いつきによる接触」が **ゼロ**になる |
| **横から入ってきた岩に当たった回数**（(C)） | 全15面で数回以下 |
| **岩が樋を通った回数** | 現行と同等かやや増える |
| つるはし1本で採れた数 | 現行と同等 |
| 落盤全体の所要フレーム数 | 現行と同等か短縮（先行のずれが消えるため） |

**(C) の回数が最も重要。** ここが多いなら、樋の配置を列で分ける方向に振る。

### あわせて測ってほしいもの（§9 の未確認箇所に対応）

| 測るもの | 対応する未確認箇所 | 判断 |
|---|---|---|
| 岩が3個以上同時に落ちた面の数と、その挙動 | §9.1 | 歩数で読めるか目視で確認 |
| **樋を通った岩の「番号」の分布** | §9.4 | **毎回同じ岩が取っているなら配置の見直し** |
| 同時に震える岩の最大数 | §9.5 | 5個以上になる面があるか |
| 落盤中に同じ走査線にかかる岩の最大数 | §9.6 | 実機で確認 |

**§9.3（(C) の頻度）と §9.4（樋の独占）が想定を外れたら、
この指示書の §2「追いつきが起きない」「歩数で読める」という前提ごと再検討すること。**
