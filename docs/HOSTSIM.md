# 面の数値化ツール (tools/hostsim)

`src/` のゲームロジックを **そのまま gcc でビルド**し、VDP/PSG だけスタブに差し替えて
ヘッドレスで走らせる。面の当たり外れを数字にして、手で15面を調整する作業を減らすのが目的。

```bash
make hostsim                                  # ビルド
make grade                                    # 面1〜15を24回ずつ採点
tools/hostsim/metrics.py --stage 7 --runs 50  # 1面だけ詳しく
tools/hostsim/sim --stage 1 --seed 3          # 生ログ (JSONL) を見る
tools/hostsim/sim --stage 7 --board           # 組み立て直後の盤面 (* = 掘らせる隙間)
```

15面 × 24回で数秒。何百回でも回せる。


## 面の配置が固定になった影響（2026-09-04）

**盤面は面番号だけで決まるようになった**（`build_stage` が配置を組むあいだだけ
種を差し替える）。`--seed` は**遊んでいる最中の揺らぎだけ**に効く。

そのため **`--runs` を増やしても、ほぼ同じ結果が並ぶ。** 以前は毎回違う盤面を
引いていたので「24回中1回クリア＝0.04」のような数字に意味があったが、いまは
**出荷される唯一の盤面を測っている**。数字の読み方が変わる。

- クリア率は 0 か 1 に寄る。**貪欲ボットは面1すらクリアできない**ので、
  いまは全面 0.0。ボットの弱さの指標であって、面の良し悪しではない
- **面ごとの盤面が1つしかない以上、その1つが悪ければ出荷される。**
  配置の種を総当たりして良い盤面を選ぶ仕組みが要る（TODO）

### 盤面の種を探す（実装済み）

```bash
tools/hostsim/sim --stage 5 --analyse            # その面の盤面を測る
tools/hostsim/sim --stage 5 --sweep 60000        # 種を総当たりして全部測る (0.5秒)
tools/hostsim/sim --stage 5 --layout-seed 805    # 種を指定して走らせる
python3 tools/hostsim/pick_seeds.py              # 面ごとに選んで表を出す
python3 tools/hostsim/pick_seeds.py --write      # src/field.c の stage_seed[] に書く
```

`--analyse` は**ボットを走らせない**。貪欲ボットは面1すらクリアできず盤面の良し悪しを
判定できないので、**岩と炭層の位置関係だけを静的に測る**。

| 指標 | 意味 |
|---|---|
| `free` | 岩の真下（同じ列）にある黒ダイヤの数＝**何もしなくても手に入る連鎖の長さ** |
| `haul` | 一番長い列へ岩を寄せるのに要る横移動の升数＝**岩の移動の面倒さ** |
| `colmax` | 一番長い縦の炭層＝一気に狙える連鎖の上限 |
| `veins` | 繋がった炭層の塊の数。多いほど散らばっている |
| `chutes` | 面に置かれた樋の枚数（低次2 / 面8以降4） |
| `taken` | **落盤ひとつで採れる黒ダイヤの数。難易度の軸** |
| `hand` | **つるはしを1本入れるだけで採れる最大数（掘らない）。難易度の軸** |
| `reach` | 炭以外を全部掘ったうえでの、1回の落下で採れる最大数（上限の参考値） |
| `bend` | **落として実際に樋で曲がった岩の数。** 0 なら板が飾りになっている |
| `combo` | そのとき届いた連鎖の長さ |
| `bump` / `side` | 落盤中に岩が**止まっていた岩へ追突**した回数 / **樋で横から入ってきた岩**に当たった回数 |
| `lost` | 落下中の岩が、**すでに折れている板の升**に着いた回数（板の取り損ね） |
| `cbend` / `nfall` | 落盤中に岩が樋を通った回数 / 落盤で落ちた岩の数 |
| `cavef` / `maxline` | 落盤が終わるまでのフレーム数 / 同じ走査線に重なる岩の最大数 |
| `noff` | 真下が黒ダイヤでない岩の数（押さないと炭層を貫かない岩） |
| **`npush`** | **そのうち、左右へ1〜2升押せば黒ダイヤの真上で止まる岩の数。** 押しは engine の `rock_push()` を1ドットずつ呼んで実際に動かす（途中で支えを失えば落ちる） |
| **`hpush`** | **ずらした岩を1つ押して揃え、一手打って採れる最大数。** 一手は「真下の黒ダイヤを割る」と「炭柱を割る（揃えた岩も落盤に加わる）」の良いほう |
| `hpbend` | `hpush` の最善手で岩が樋を通った回数 |
| **`rowdup`** | **岩が2個以上ある行の数。0 が必須**（横一列8枚のスプライト制限） |
| **`hprep`** / `hprepbend` | **ずらした岩を全部揃えてから炭柱を割って採れる数** / そのとき樋を通った回数。岩ごとに `hpush` で一番よかった押し方をまとめて行う |
| `cbal` / `rbal` | 左右の散らばり。少ない側の黒ダイヤ／岩の割合（%）。0 = 片側だけ、50 = 均等 |
| `wet` / `wseal` | **出水の面（面7）だけ。** 落盤から60秒で水になった升の数 / 四方が全部水になって叩けなくなった黒ダイヤの数（**0 が必須**）。`--water` で盤面を升で出せる（`~` が広がった熱水、`=` が溜まり湯） |
| `pool` | **溜まり湯**（面10から。最初から止まっている熱水）の升数。面10・11=1、面12・13=2、面14・15=3 |
| `rail` / `railrock` / `railpay` | **鉱車（面10から）。** レールが置けたか / レールの上の列にある岩の数（載せる物） / **車止めから岩を落として実際に採れる黒ダイヤの数**（降ろす先の見返り）。どれも1以上が必須。`--cart` で面ごとに見られる |
| `hpick0` | **炭柱以外を1枚割って採れた数（樋は問わない）。** 樋を置かない第一坑（面1〜3）での「指でなぞれる一本の線」の保証 |
| **`par`** | **邪魔されずに掘ったときの所要フレーム数。** 出発点から黒ダイヤ全部と水風呂を近い順に回り、掘り (24f/升)・歩き (16f/升)・つるはし (耐久×18f) を足す。**下限寄りの見積もり**で、敵・岩待ち・二度目の風呂・連鎖の短縮は入っていない |
| `dpar` | その道中で**新しく掘る升の数** |
| `bathd` | 出発点から水風呂までの**フレーム数**（風呂の遠さ）。**升の数では測れない** — 風呂は必ず掘ってある升に置かれるので掘削数は全面0になる（2026-10-13 の実測） |
| `parleft` | `par` の経路で**届かなかった黒ダイヤの数**。0 でなければ盤面がおかしい |
| **`gapn`** | **下ごしらえを仕込んだ鉱脈の本数**（縦に土を挟んだ鉱脈。`src/field.c` の `vgap_tbl`） |
| **`digpay`** | **隙間を掘ったぶん増える黒ダイヤの数。** 掘らずに落とした場合との差を、engine を回して測る |
| `digmin` | 1本あたりの最小。2本仕込む面で「片方が死んでいる」を弾く |
| `digcells` | そのために掘る升の数（段取りの重さ） |

`taken` `reach` `bend` `combo` は**エンジンを回して測る**。とくに `reach` は
板の向き・曲がった先が掘れるか・その列に炭があるか、が全部絡むので盤面を眺めても
分からない。

**`hand` の測り方**は「盤面をそのまま使い、黒ダイヤ1枚だけを耐久ぶん叩く」。
盤面上の全部の黒ダイヤを順に試して一番良い結果を採る（どれを叩くかはプレイヤーが
選べるため）。炭柱を叩けば落盤もそこに含まれる。**遊んだときに実際に起きることを
測っている唯一の指標**で、種選びの軸はこれ。

**`reach` の測り方**は「プレイヤーが掘りたいだけ掘れたら」の上限。
炭以外の升を全部掘り、**岩を1つだけ残して**落とし、採れた数を数える。
真下が黒ダイヤなら1枚だけ割っておく（黒ダイヤは静止した岩の支えなので、
割らないと岩は一歩も動かない ＝ ゲーム側で言う「1枚ぶんの手間」）。
掘る手間そのものは別の指標（`haul`）が持つ。

`pick_seeds.py` には2つの仕組みがある。

- **`REQUIRE`** … 満たさない種を候補から外す（**全面で `hbend>=1` と `rowdup==0`**。
  ずらす岩のある面では `npush` ≥ ずらす数、`hpush` ≥ `hand` + 2、2個以上ずらす面では
  `hprep` ≥ `hpush` + 2。全面で `cbal`・`rbal` ≥ 30）。15面を並列に総当たりする
- **`PINNED`** … 点数では選べないときに、実行して見比べて決めた種を固定する（いまは空）

狙いの表は `pick_seeds.py` の `TARGET`（つるはし1本で採れる数）。面1の5個から面15の1個まで
下げつつ、**幕の頭（面4・7・10・13）だけ1つ上げる**（新しい仕掛けを触っている間も採れるように）。
結果は `docs/GAME_RULES.md` §11 にある。

## 仕組み

| ファイル | 役割 |
|---|---|
| `tools/hostsim/stubs.c` | VDP・PSG・スプライト・文字・絵データのスタブ。入力もここからボットが注入する |
| `tools/hostsim/sim.c` | 通行グラフの BFS、ボット、毎フレームの JSONL 出力 |
| `tools/hostsim/metrics.py` | JSONL を読んで採点する。しきい値と合格条件はここ |

**ゲームのロジックには一切手を入れていない。** `field.c` / `enemy.c` / `player.c` /
`rock.c` / `bomb.c` / `bonus.c` を実機と同じソースのままリンクしている。

### 型を合わせてある

`src/msx.h` は `HOSTSIM` が定義されているとき `<stdint.h>` を使う。MSX 側は
`int` が16bitなので、ホストで32bitのまま走らせると**桁あふれの挙動が変わり、
シミュレーション結果が実機と食い違う**。

### 計測のために公開した変数

`en_morph` / `en_ghost` / `en_warm` は本来 static だが、透明化と点滅の状態が
読めないと危険度が測れないので公開している (`en_rest` と同じ扱い)。実行時の
コストは無い。

先読み (後述) のために `en_dir` と `en_stun_t` も公開した。向きが分かれば
「いま通り過ぎた敵は引き返せない」ことが読め、よろけの残りが分かれば
「この敵はあと何フレーム止まっているか」が読める。

## 危険度の測り方

**ユークリッド距離では測らない。** `cell_link[]`（掘り跡に残る土の膜）があるため、
1升隣に居ても膜で隔てられていれば敵は来られない。危険度は必ず**通行グラフ上の距離**で測る。

- **到達余裕 `T_reach`** = 一番早く自機の升へ来られる敵の所要フレーム数。
  敵の速度は種類ごと (`SPD_RED`..`SPD_ORANGE`)、透明化中は `SPD_GHOST`。
  湧いて点滅中 (`en_warm`) の敵はまだ当たらないので除外する
- **退路数 `E`** = 隣の4方向のうち、そこへ動くと `T_reach` が増える向きの数。
  0 か 1 なら追い詰められている

## 指標

| 指標 | 定義 | 意味 |
|---|---|---|
| **ヒヤリ** | `T_reach` が1.0秒を下回った瞬間 | 緊張感の1単位 |
| **爽快** | ヒヤリが0.5秒以内に解消し、その間に得点が入った | 緊張を自分の手で解消した |
| **麻痺** | `T_reach` < 1.0秒 が5秒以上続く | 危険が常態化して意味を失っている |
| **凡死** | 退路0の状態でヒヤリに入った | 判断で避けられていない |
| **退屈** | 敵が3秒以上遠く、報酬も無い | 掘るだけの時間 |
| **放出量** | 0.3秒窓の (得点 + 鳴った効果音) のピーク | どれだけ派手に解消したか |

爽快感は「解消したか」(率) と「どれだけ派手に解消したか」(振幅) の掛け算。

## 使うときの約束

- **これは「面白さ」ではなく「面白さの必要条件の欠落」を測る道具。**
  ヒヤリ0回の面はつまらないと断言できるが、ヒヤリ5回の面が面白いとは断言できない。
  **否定側にだけ強い**
- **目的関数にしてはいけない (Goodhart の罠)。** ヒヤリ回数を最大化しにいくと
  「敵を増やして通路を狭くする」のが最適解になり、理不尽な面ができる。
  **合格/不合格のゲートとして使う**
- **しきい値はまだ較正していない。** 1.0秒 / 0.5秒 / 3.0秒 は暫定値で、
  人に遊んでもらって「ヒヤッとした瞬間」の申告と突き合わせて合わせる必要がある

## ボットは2つある (`--bot`)

| | 中身 | 成績 (面1〜15 を各48回 = 720回) |
|---|---|---|
| `greedy` (既定) | 次の一升しか見ない。「体温が1/3を超えたら風呂、でなければ一番近い黒ダイヤ」 | 約 50/720 |
| `smart` | **掘る時間込みの最短路**を毎升引き直す (ダイクストラ) ＋ **敵の先読み** | **241/720** |

**16回では足りない。** 以前は 16回 (240) で測っていたが、重みを変えたときの差が
雑音に埋もれる。実際、16回で「良くなった」と見えた設定が 48回では悪化していた。
**調整に使った種とは別の種で検証する**こと (`SEED0` を変えて2回測る)。

`smart` の重み付け。**罰則はすべて「何升ぶん遠回りしてよいか」の尺度**に揃えてある
(掘り済み16 / 土24 が基準)。以前 200〜1400 を足していたときは実費を押し潰し、
経路が「敵から最も遠い道」になって延々と遠回りし、全面で過熱死した。

| | 重み |
|---|---|
| 黒ダイヤ | 耐久 × `PICK_FRAMES` + 24 |
| 熱水 | +96 |
| 岩の升 / その真下 | +48 / +96 |
| 鉱車のレール行 | +64 (鉱車の居る升は +400) |
| 敵が来られる升 | `(128 − 来るまでのフレーム数)` (下記「敵の先読み」) |
| ガス (裏面) | 通らない |

### 敵の先読み (2026-10-28)

**「何歩先に敵が居るか」ではなく「何フレーム後に敵が来られるか」で測る。**
歩数で測ると 25px/s の橙と 35px/s の赤が同じ危険度になるが、3升先から来るのに
114 フレームと 81 フレームの差がある。重みの尺度がそのまま使えるのは偶然ではなく、
自機は `SPD_TUNNEL == SPD_UNIT` なので1升 16px を 16 フレームで渡る =
掘り済みの升の重み 16 と同じだから。**この重みは「フレーム」と読み替えてよい。**

入れて効いた項 (720回 × 2通りの種で確認):

| 項 | 中身 | クリア |
|---|---|---|
| 速さだけ | 種ごとの `kind_spd` でフレームに直す | 210/720 (先読み前と同じ) |
| ＋ **よろけ** | `en_stun` の残りぶん来られない | 235/720 |
| ＋ **点滅** | `en_warm` のあいだは動かないし当たらない | 241/720 |
| ＋ 引き返さない | `decide_dir` は引き返しを候補から外す | 241/720 (ほぼ誤差) |

**いちばん効いたのは「よろけ」。** 潰した敵の横を通れるようになるので、
「先頭を潰して通り抜ける」という設計どおりの手をボットが打つようになった。
面2 は 5/48 から 46/48 へ変わった。

入れても効かなかった項 (どちらも外してある):

- **透明化の予兆** (`en_morph`)。「あと N フレームで土をすり抜けてくる敵」を
  直線距離で見る項。`SPD_GHOST` は這う速さ (1升 128 フレーム) なので、
  坑道を歩いて来るほうがほとんど常に早く、入れると地平が埋まって勾配が消えた
  (241 → 234)。**いま透明な敵は直線で見る** (坑道を歩いていないので、
  そうしないと見えなくなる)。
- **落ちてくる岩**。歩数で測っていた頃は岩の真下を最大の危険としていたが、
  `bot_cost` が岩そのものに罰則を持っているので二重だった (241 → 240)。

死因の内訳 (`smart`、720回): クリア241 / 敵448 / 過熱16 / 鉱車10 / 岩5。
**過熱死と岩死はほぼ消えた** (先読み前は過熱177 / 岩43)。残っている穴は敵で、
次がダイナマイトを一度も使わないこと。

### 溜め打ちは「掘る技」ではなく「逃げ道を残す技」

「敵が来るまでの時間で溜めの段を決め、間に合わないなら弱く叩く」を入れたら、
クリアが 241 → 216 へ**落ちた**。1振りあたりの時間は連打のほうが短い
(18 対 32 フレーム) のに悪くなるのは、**中断できるかが違う**から。

- **振り** (`swing` = `PICK_FRAMES`) のあいだは動けない (`player_update` が早期 return)。
- **溜め** (`charge_t`) のあいだは動ける。動けば溜めが切れるだけ。

威力3まで溜めると 96 フレームのうち動けないのは2回の振りの 36 だけで、残り 60 は
敵が来たら逃げられる。弱く連打すると 18 フレームごとに振りが入って**ずっと動けない。**
**溜め打ちが強いのは、掘るのが速いからではなく逃げる隙があるから。**

風呂へは**到着時の体温の見積もり**で立つ。`bot_h[]` に経路に沿った発熱
(つるはし1振り = `HEAT_PER_SWING`) を伝播させ、`温度 + 見積もり + BOT_SLACK`
が上限に届いたら目標を風呂へ替える。**一律のしきい値 (例「体温が7割で風呂」) は
かえって悪い**: 過熱死は消えるが、冷やしに行く移動そのものが敵への曝露なので
敵死が3倍になり、通算のクリアは 70 → 43 まで落ちた (実測)。

**重みへの過敏さに注意。** 罰則を1つ足しただけで、通算のクリアが 70 → 44 へ落ち、
しかも**面ごとの成績が入れ替わった** (面1 が 15/16 → 0/16、面3 が 1/16 → 16/16)。
したがって **面ごとのクリア率をその面の難しさとして読んではいけない。**
読めるのは通算と、死因の内訳のほう。

**地平 (`FC_HORIZON`) も過敏。** 96/128/160/192 で 171/241/194/222 と跳ねる。
128 は別の種でも 238 を出したので採ったが、**この手の数字は調整に使った種だけで
決めてはいけない。**

## いまのボットの限界 (重要)

`smart` でも面3・6・8〜15 はほぼ抜けられない (面1・2・4・5・7 は抜ける)。

したがって:

- **面をまたいだ絶対値の比較には使えない。** 面10の数字が悪いのは、面10が悪いのか
  ボットが弱いのか区別がつかない
- **同じ面での前後比較には使える。** ルールを変える前と後を同じボットで測れば、
  差はルールの効果である
- **麻痺・凡死・詰みの検出は比較的信用できる。** ボットの強さにあまり依存しない

面をまたいだ比較をしたいなら、まずボットを強くすること (ダイナマイトを使わない、
岩を利用しない、先読みしない、といった穴がある)。

### 1. 面エディタと数値化ツールの連動 (本命)

**別ツールとして作る。MSX 側には持たせない。** 編集ツールが吐いた面を、そのまま
`sim` にかけて採点できる状態を目標にする。

```
   面エディタ  ──(面データ)──▶  sim  ──(JSONL)──▶  metrics.py  ──(採点)─┐
        ▲                                                              │
        └──────────────── 合否と指標を editor へ返す ────────────────────┘
```

**接続点はもう出来ている。** `sim --stage N --seed S` の1行目 (`type:"stage"`) に
盤面が `grid` として入っている。

```
 0 |.............O..|      . =土      空白=坑道
 1 |....... .....5..|      数字=黒ダイヤの耐久 (炭柱は大きい)
 5 |....222B......O.|      x=割れた黒ダイヤ  O=岩
 6 |.......p2.....5.|      B=水風呂  N=湧き出し口  p=火薬
 9 |..... ppppN.....|
```

必要な作業:

- [ ] **面データ形式を決める。** いまの `grid` 表記をそのまま入力にも使えるようにする。
      16列×11行の文字列配列＋メタ情報 (面番号・黒ダイヤの耐久・敵のプール数)。
      `tools/gamedata` の JSON と同じ流儀に揃えると、エディタ側の実装を共用できる
- [ ] **`sim --load <file>` を足す。** `build_stage()` の代わりに面データを流し込む。
      `dug[] / coal[] / cell_link[] / 岩 / 風呂 / 湧き出し口 / 自機の出発点` を
      直接組み立てるので、`field.c` に「外から与える」入口が1つ要る
- [ ] **`metrics.py --load <file>` を足す。** 面番号ではなくファイルを採点できるようにする
- [ ] **エディタ本体。** `MsxPatternStudio` と同じく別セッション・別ツール。
      置いた瞬間に採点が回って「この面はヒヤリが少なすぎる」と返るのが理想

**未決の設計判断 (先に決める必要がある)**:

**手で作った面が、いまの自動生成を置き換えるのか、併用するのか。** 現在は
`set_stage_layout()` が数字の形を掘り抜いて乱数で配置しており、面データは存在しない。

| | 生成のまま | 手で作った面に置き換え |
|---|---|---|
| ROM | 増えない | 面15枚ぶんのデータが要る (バンクへ逃がせば容量は問題にならない) |
| 手間 | 0 | 15枚を人が作る |
| 品質 | 当たり外れが出る。振り直しで対処 | 狙って作れる |
| 遊び | 毎回違う | 覚えられる (パックマン型) |

**併用案**: 生成は残したまま、`metrics.py` の合格条件を外れた配置を**その場で振り直す**
(生成 → 採点 → 不合格なら再生成)。これなら面データも手作業も不要で、当たり外れだけ消せる。
エディタは「特定の面だけ手で作る」用途に絞る。

### 2. ボットを強くする

面をまたいだ絶対値の比較をするために要る (上記「いまのボットの限界」)。
経路の先読みと敵の先読みは入ったので、残っているのは:

- **ダイナマイトを使わない** (`sim_trig_b` は常に0)。敵を吹き飛ばす手が丸ごと無い。
  死因の 62% (720回中448回) が敵なので、ここが最大の穴。
- **岩を利用しない**。落として黒ダイヤを割る手も、敵を潰す手も打たない。
- **掘る順を考えない**。いまは「一番近い黒ダイヤ」へ行くだけで、
  掘ったあとの坑道の形 (袋小路になるか、逃げ道が増えるか) を見ていない。

### 2b. 面ごとの「感情」を数にする (`tools/hostsim/emotion.py`)

`make emotion`。敵圧・熱圧・袋小路から**ストレス**を、連鎖と放出量から
**爽快感**を作り、「ストレス高＋爽快感高 → カタルシス」「ストレス高＋爽快感低 →
理不尽」のように判定する。しきい値は**まだ較正していない**ので、
面どうしの比較にだけ使う。詳しくはそのファイルの説明にある。

### 3. 順序依存度

炭層の採掘順を全探索し (面15でも 4! = 24通り)、クリア時間の変動係数を出す。
0.05未満なら「掘る順序に意味が無い」。**炭柱が効いたかどうかがこれで判定できる。**

### 4. 詰みの自動検出

岩が割れた黒ダイヤの升に居座ると回収不能になる問題は `coal_crush_at()` で塞いだが、
同種の詰み (全採掘を満たせなくなる状態) を自動で見つける検査を足す。
今回は人が気づいたが、次は気づかないかもしれない。

### 5. 「どこを直せばいいか」が見える数値

いまの指標は**合否のゲート**でしかない。「面7は爽快率が低い」までは出るが、
**何をどう直せば上がるのか**が出ない。処方に繋がる数値を足す。

盤面ごとの偏りを出すもの:

- [ ] **升ごとのヒートマップ** — 死亡位置 / 滞在時間 / ヒヤリの発生位置。
      特定の升に死が集中していれば、そこが理不尽な配置
- [ ] **未到達率** — 一度も踏まれなかった升の割合。高ければ盤面の一部が死んでいる
- [ ] **黒ダイヤごとの採掘コスト** — その1個を採るまでの移動距離・所要時間・
      その間の平均 `T_reach`。遠すぎる/近すぎる配置を名指しできる
- [ ] **水風呂の往復** — 入った回数、1回あたりの往復距離、入る直前の体温。
      近すぎれば緊張が消え、遠すぎれば詰む。**適正距離を数字で決められる**
- [ ] **湧き出し口の距離** — 自機の出発点・炭層・水風呂それぞれからの通行グラフ距離

要素が死んでいないかを見るもの:

- [ ] **岩の不発率** — 一度も落ちなかった岩の割合。高ければ岩が飾りになっている
- [ ] **炭柱の機能率** — 割った結果、岩が落ちて敵を潰した割合。
      **炭柱が狙いどおり働いているかの直接の判定**
- [ ] **火薬の未使用率 / ボーナスの未接触率** — 高ければその要素は面に効いていない
- [ ] **梅干しの発生と回収率** — 倒した敵の落とし物が拾われているか

指標から処方へ:

- [ ] **ゲートを外した指標に対して、原因の候補を返す。**
      例: ヒヤリ不足 → 湧き出し口が炭層から遠い / 退屈が多い → 黒ダイヤが固まりすぎ /
      凡死が多い → 袋小路の奥に黒ダイヤがある。**面の振り直しではなく、
      どの配置をどちらへ動かすかを示せるところまで持っていく**

### 6. しきい値の較正

1.0秒 / 0.5秒 / 3.0秒 は暫定値。3〜5人に遊んでもらい、ヒヤッとした瞬間・気持ち
よかった瞬間を後から申告してもらって合わせる。申告なしでやるなら、
**入力ログの方向反転頻度**がパニックの代理変数になる。
