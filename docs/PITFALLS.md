# つまずいた点（実装メモ）

**同じ穴に二度落ちないための記録。** MSX2 の VDP と ROM まわりで実際に時間を溶かしたものを、
症状と原因の形で残してある。もとは README に置いていたが、README を読み物として整理した
ときにこちらへ移した（2026-10-21）。

遊びのルールは [GAME_RULES.md](GAME_RULES.md)、置き場（固定領域・窓・RAM 実行）の約束は
リポジトリ直下の `CLAUDE.md` にある。

---

## VDP コマンドエンジン

- **コマンドコードは `1000`=LMMV / `1100`=HMMV。** `0xC0` を LMMV と取り違えると
  バイト単位の塗りになり、SCREEN 5 では1ピクセルおきに色0が残る（縦縞になる）。
- **コマンドレジスタを R#17 の間接ポート（0x9B）へ `OTIR` で流すと取りこぼす。**
  NY が化けて画面全体を塗る暴走コマンドになり、CE が下りずハングした。
  R#36..R#46 を通常のレジスタ書き込み（値 → レジスタ番号）で送れば確実。
- **コマンド発行直後は S#2 の CE がまだ立っていない。** そこで完了待ちをすると「終わった」と
  誤判定し、実行中のコマンドの上から DY/NX/NY を書き換えてしまう（エンジンがこの3つを
  作業用に更新するため暴走する）。CMD 書き込み後に短い待ちを入れる。
- **VDP コマンド実行中に CPU から VRAM を触らない。** OAM 転送やスプライト色の書き込みの
  前にも CE の完了を待つ（`vdp_setwrite` / `oam_flush` の先頭で待つようにしてある）。

## VDP のポートと割り込み

- **ポート 0x99 への2バイト書き込みは first/second フリップフロップを使う。**
  BIOS 割り込みが割って入ると壊れるので、VDP アクセスは DI/EI で囲む。
- **垂直帰線待ちで「次の JIFFY 変化」を待つと、1フレームが 16.7ms をわずかに超えただけで
  60fps → 30fps へ半減する**（移動が1フレーム1pxなので速度もそのまま半分になる）。
  既に遅れている場合は待たずに進めると、落ち方がなだらかになる。

## スプライト

- **16x16 スプライトの VRAM 並びは「左半分16バイト → 右半分16バイト」。** 行交互に書くと
  絵が崩れる。作画は `spr_pattern_rows()`（16行 x 16bit の表）を使う。
- **パーク Y は 212。** 216 は mode 2 の行終端マーカーなので使わない。
- **Y 座標 225〜255 は負（-31〜-1）として扱われる。** 画面の上から入ってくる絵のための
  仕様で、行0 に置いた絵は Y=255 になる。素直に足す道具を書くと「写らない」と誤診する
  （`tools/vram2png.py` で実際にやった）。

## 文字と ROM

- **文字描画は1行につきアドレス設定1回にする。** 文字ごとに設定し直すと6桁のスコアで48回
  必要になり、実測で処理時間の1割強を占めていた。
- **32KB を超えるカートは BIOS がページ2を有効化してくれない。** `crt0` で ENASLT を呼ぶ。

## 音源を足したときに踏んだもの（2026-10-23）

- **SDCC の `--sdcccall 1` は最初の引数をレジスタに載せる。** asm のラッパを
  「引数はスタックから」で書くと、黙って別の値を読む。BIOS の RDSLT をそう書いたせいで
  **内蔵 MSX-MUSIC を見つけられなかった**（`opll_hw = 0`）。
  **引数は変数で渡す**形にすれば規約に左右されない（`src/bios.s` の `rdslt_go`）。
- **検出は設定の初期化より後に呼ぶ。** 検出のしまいで「検出できたか && 設定が ON か」を
  見ているので、`config_init()` より前に呼ぶと設定がまだ 0 で、**載っている機械でも
  鳴らない**。音が出ないので気付きにくい（`pcm_use` を読んで初めて分かった）。
- **走査線割り込みは2行間隔では間に合わない。** 割り込みの入口（BIOS の H.KEYI 経由）と
  VDP のポート待ちで1回 100µs 以上かかり、127µs の間隔に**1回おきに取りこぼす**。
  取りこぼしは「音が出ない」ではなく「**音が半分の速さになる**」形で出る。
  録音した太鼓の基音が設計の 80Hz ではなく 40Hz だったことで気付いた。
  **4行間隔（3,925Hz）なら等間隔で出せる。**
- **割り込みの中でバンク窓を借りるなら、戻す先を変数で控える。** `bank_select` は
  **控えを先に書いてから**ハードを切り替えること。逆にすると、その隙に割り込んだ
  ISR が古い向き先へ戻してしまい、戻ってきたコードが別のセグメントを読む。

## 音が「鳴っているのに聞こえない」ときに見たもの（2026-10-24）

- **「鳴っているか」はレジスタで、「聞こえるか」は帯域で確かめる。** 太鼓は4秒に20発、
  拍と1発ずつ対応して正しく鳴っていたのに、作者には聞こえなかった。エネルギーが
  **300Hz 以下に集まっていた**のが理由で、ノートPCのスピーカーはそこを出せない。
  **250Hz 以上だけを通してから実効値を取る**と、聞こえ方と同じ順に並ぶ。
- **音源ごとに分けて録る。** openMSX の `<音源>_ch<n>_record` に書き込み先を入れると
  チャンネル単位で wav が落ちる（**音量を触らずに**分けられる。`set <音源>_volume 0` は
  設定ファイルに保存されてしまうので使わない)。
  **チャンネルの並びは推測しない** — ハイハットを数えようとして melody の ch7-9 を
  録り、「FM のリズムが鳴っていない」と誤診した。鳴っているかはレジスタ（R#0E の
  打種ビット）を数えるほうが確実。
- **邪魔をしているものを測らずに決めない。** 「ノイズドラムが太鼓を覆っている」と考えて
  完全に止めてみたら、PSG 全体の実効値は 1703 → 1694 しか動かなかった（覆っていたのは
  主旋律）。**止める前に、止めた版を作って測る**と1回で分かる。
- **飽和（`tanh`）の前に足した成分は消える。** 撥の当たりを 0.42 混ぜても、胴の大きな
  低い波に乗っているので潰され、正規化と量子化のあとには 800Hz 以上が全体の 0.3% しか
  残らなかった。**潰したい音と潰したくない音は、飽和の前と後に分ける。**
- **擬似乱数は範囲と種を確かめる。** `(seed >> 15) / 32768.0 - 0.5` は -0.5〜+1.5 で、
  平均が +0.5 ずれていた（雑音ではなく正の盛り上がり）。さらに種を3音で共有していたので
  **生成の順番で音が変わり**、同じ設定の測定値が3割ずれた。測定を疑って遠回りする前に、
  **生成器が決定的かどうか**を見る。

## 変数は 0 で始まらない (2026-10-26)

**`src/crt0.s` は変数領域を 0 で埋めない。** 初期値つきの変数 (`_INITIALIZED`) を
ROM から写すだけで、初期値の無い変数は**電源投入時の RAM の中身がそのまま残る**。

裏面の旗 (`loop_n`) を足したときにこれを踏んだ。遊んでいる間に 1 になる変数で、
起動時に書く場所が無かったため、**C-BIOS の機械では最初から裏面で始まった**
(実機 turbo R ではたまたま 0 だったので気付かなかった。スモークテストを
両方の機械で回していて見つかった)。

**起動時に 0 である前提の変数は、`config_init()` のような一度だけ走る場所で
明示的に書くこと。** 面の組み立てやミスの復帰で毎回書かれる変数は問題ない。

## 計測の道具が「人と違う遊び方」をしていた (2026-10-26)

**ボットが全面で過熱死する原因は、ボットではなく計測の道具 (`tools/hostsim/sim.c`)
のほうだった。** つるはしの押し方がこう書いてあった。

```c
player_pick((uint8_t)(swing_pow < CHARGE_MAX));   /* 間違い */
```

対象の有無に関係なく**常に押している**ので、歩いている間もずっと溜まり続け、
78フレームごとに威力3の空振りが出ていた。`do_swing()` は空振りでも発熱する
(それ自体は正しい仕様) ので、**歩くだけで毎秒12ほど余計に発熱**していた。
時間経過ぶん (毎秒4) の3倍で、どのボットも面3以降は16回中16回オーバーヒートした。

直したのは押す条件だけ。

```c
player_pick((uint8_t)((face_coal_now || bot_want_pick) && swing_pow < CHARGE_MAX));
```

これで過熱死は 240回中 59回まで下がり、死因の最多は敵との接触に変わった。

**見つけ方が教訓。** 「賢くしたのに成績が落ちる」ので、1フレームごとの体温の
差分を並べた。**+12 と +4 が、位置に関係なく78フレームごとに規則正しく**入って
いた。場所によらず周期的なら、原因は盤面ではなく**入力のほう**にある。

さらに言えば、**ボットの成績が悪いときは、まずボットを疑う前に道具を疑う。**
`after time` の括り方で「機械がリセットしている」と誤診したのと同じ構図で、
ここでも**測定の仕掛け自身が結果を作っていた**。

**この不具合は 2026-10-26 より前のボット由来の数字すべてに乗っている。**
`make grade` の合否や、それを見て決めた面の調整は、必要なら測り直すこと
(`par` は解析で出しているので影響を受けない)。

## 調整に使った種のままで良し悪しを決めていた (2026-10-28)

敵の先読みを入れて重み (`FC_HORIZON`) を掃いたら、16回 × 15面 = 240回で
「70 → 76 に増えた」と出た。**48回 (720回) で測り直したら 210 → 188 で、
むしろ悪くなっていた。** 240回では差が雑音に埋もれていて、しかも
**その雑音の山をめがけて重みを合わせていた**（過適合）。

直したのは測り方のほう。

- **回数を増やす** (240 → 720)。sim は速いので数秒しか変わらない。
- **調整に使った種とは別の種でもう一度測る** (`SEED0=0` と `SEED0=100`)。
  採った設定は 241 と 238 で揃ったので、これは雑音ではないと言える。

`docs/HOSTSIM.md` には前から「重みへの過敏さに注意」と書いてあったのに、
**同じ罠に同じ道具で落ちた。** 注意書きがあるだけでは防げない。

### ついでに、思いついた理由をそのまま書かずに済んだ話

「溜めを最大まで溜めるほうが強いのは、**溜め打ちが前方2升の敵を6秒止めるから**」と
考えて、そう書きかけた。もっともらしいが、**測ったら違った**——よろけ段の平均は
0.341 対 0.368 でほとんど変わらない。本当の理由は
「**溜めている間は動けるが、振っている間は動けない**」だった（`docs/HOSTSIM.md`）。

因果の説明を書く前に、その因果が出るはずの量を1つ測る。ここでは
1フレームごとの `en_stun` の和を記録に足すだけで済んだ。

## 検査の道具が静かに嘘をついた話 (2026-10-30)

`field.c` を「面の組み立て」と「描画」に割って 0x8000 の窓へ追い出すとき、
**境目を跨ぐ `static` が無いこと**を先に確かめたかった。書いた確認はこれ。

```sh
awk -v v="$v" 'NR>=1082 && $0 ~ "\\<" v "\\>"' src/field.c | wc -l
```

全部 0 件と出たので「一つも跨いでいない、きれいな境目だ」と判断した。
**実際は `draw_tile` が跨いでいた**（コンパイラが `implicit declaration` で教えてくれた）。
原因は **BSD awk の ERE に `\<`（単語境界）が無い**こと。パターンが何にも一致せず、
**一致0件は「跨いでいない」ではなく「検査していない」だった。**

同じ日に同じ型の間違いをもう一度やった。窓の向こう側を呼んでいないかを調べる
`tools/win2check.py` の最初の版は、関数の置き場を**リンクマップから**引いていた。
`.map` には `static` の記号が出ないので（この文書の別項と `CLAUDE.md` に前から
書いてある）、`static` が全部「どこのものでもない」ことになり、
**53 個ある組み立て側の関数のうち検査できていたのは数個だけ**だった。
置き場は `.asm` の `.area` 指令から引くように直した。

教訓は「**検査が「問題なし」と言ったときほど、検査そのものを疑う**」。
具体的には、通す前に**わざと壊して赤が出ることを確かめる**。`win2check.py` は
2通りで確かめた。

- 組み立ての中に `player_carve()` を1行足してコンパイルし直す
  → `1. 組み立て (build_stage) から PLAYCODE へ: ['_player_carve']` で赤
- `_build_stage` を障壁から外す → 遊ぶ側から組み立ての中身が全部見えることになり赤

**赤を見ていない検査は、緑を信じる根拠にならない。**

## コンパイラが誤った機械語を吐いた話 (2026-10-25)

**エンドロールが1文字も出なかった。** スクロールはしているのに、ページ1 には1画素も
書かれていない。原因は C でも VDP でもなく、**SDCC が吐いた機械語**だった。

```
;src/ending.c: vdp_fill(0, (uint16_t)(PAGE1 + band), ...)
        ld      a, l
        add     a, #0xe0
        ld      e, a          ; E = band の下位
        inc     d             ; ← D を 0 にしないまま「+256」している
        push    de
```

`band` の上位バイトを作る命令が無く、**D には直前の比較で使った値が残っていた**。
結果、書き込み先が 0x8808 ではなく 0x0808 (ページ0) になり、表示しているページ1 には
何も出ない。**絵は出ているのに1文字も出ない**という形で現れる。

| | |
|---|---|
| 版 | SDCC 4.6.0 #16555 |
| 出る条件 | **`--sdcccall 1`** (4.1.12 以降の既定)。`--opt-code-speed` / `--opt-code-size` / `--no-peep` のいずれでも出る |
| 出ない条件 | `--sdcccall 0`。ただし本プロジェクトは asm のラッパをこの規約で書いているので戻せない |
| 引き金 | 早い `return` を持つ分岐の中で 16ビットの計算をしていると、後ろの経路で「上位バイトは 0」と誤って覚える |
| 最小再現 | `tools/sdcc_regalloc_repro.c` (ビルドには入らない) |

**上流に同じ報告は見当たらない** (2026-10-25 に SDCC の課題管理を確認)。近いのは
[#4103](https://sourceforge.net/p/sdcc/bugs/4103/)「z80: peephole 36 drops `ld a, #n`
although a is still used (wrong byte argument with `__sdcccall(1)`)」で、**同じ 4.6.0 #16555
に対する報告**だが、あちらはピープホールの規則が原因で `--no-peep` では出ない。
こちらは `--no-peep` でも出る (しかも上位バイトを **C** に置いて **D** を使う) ので別物。
**4.6.0 がリリース版の最新** (Homebrew も同じ) で、#4103 の修正 (r16955) も未リリース。

**回避**: 16ビットの組み立てを**別の関数へ出す** (`src/ending.c` の `page1_y()`)。
関数の頭ではレジスタの思い込みが無いので、素直に `ld d,#0x00` が出る。

**気付く仕組み** (作り込みすぎない形で2つ):

1. **実行中に見張る。** エンドロールの最中は、書き込み先が必ずページ1 (bit15 が立つ)。
   openMSX で `_vdp_setwrite` を捕まえて確かめる (**番地はビルドごとに `.map` から取り直す**。
   **ロールの最中だけ**で、ほかの場面はページ0 へ書くのが正しい)。

   ```tcl
   debug set_bp 0x405D {} { if {([reg hl] & 0x8000) == 0} { puts "BAD HL=[format %04X [reg hl]]" } }
   ```

2. **書く前に grep する。** ページの定数と8ビットの値を足している箇所を洗う。
   見つかったら `page1_y()` のような**専用の関数経由へ揃える**。

   ```bash
   grep -nE "\b(256|512|768|1024|0x0?[1-9a-fA-F]00|PAGE1)[[:space:]]*\+|\+[[:space:]]*\b(256|512|768|1024|PAGE1)\b" src/*.c
   ```

   **256以上の定数との足し算だけ**を見る。`(uint16_t)(x + 3)` のような、もともと
   16ビットの値に小さい定数を足す形まで拾うと件数が多すぎて誰も見なくなる
   (最初に広く書いて実際そうなった)。いまは `src/ending.c` の2件
   (関数の定義と説明) しか出ない。

**見つけ方**: 「描いているはずなのに出ない」ときは、`build/*.asm` の該当行を見る。
**`inc d` / `inc h` / `inc b` で 256 を足している箇所の直前に、その上位バイトを
置く命令があるか**を確かめる (ループ変数の増加と見分けること)。
実機で追うなら openMSX の `debug set_bp` で `_vdp_setwrite` を捕まえ、`reg hl` を見る。
**書き込み先の番地が分かれば、どのページへ書いているかで一発で分かる。**

## 「全部の行数」で止める位置を決めていた話 (2026-11-07)

**エンドロールの最後の `PUSH SPACE KEY` が画面の上へ流れていき、真っ暗な画面が
9秒続いてから戻ってきた** (作者の報告、表のエンディング)。裏も同じ病で、こちらは14秒。

エンドロールは「終わりの塊 (献辞〜案内の10行) を、流れている途中と**同じ位置**で
止める」作りになっている。止める画素数は

```c
#define ROLL_END ((uint16_t)(END_ROLL_N - ROLL_TAIL) * ROW_H + LEAD - ROLL_TOP)
```

と**文面の総行数 `END_ROLL_N` (99)** から出していた。ところが**流す行は総行数より
少ない**。物語が2本あって、表は裏の20行を飛ばし、裏は表の25行を飛ばすからで、
実際に用意する帯は表79本・裏74本しかない。差のぶん (表 320画素・裏 400画素) だけ
余計に流れ、塊が上へ抜けきってから置き直していた。

**直し方**: 止める位置も**実際に流す帯の数**から出す (`roll_end()`)。

**一般化すると**: *一覧の一部を飛ばして回すのに、終わりの判定だけ一覧の長さから
作っていた。* 飛ばす経路を足した日に、長さと仕事量が別の数になる。
**「何個あるか」と「何回やるか」は別の変数**として扱うこと。

**測り方** (openMSX。隠しコンフィグの `SEE ENDING` から入れば数十秒で確かめられる):

- R#23 (垂直オフセット) は8ビットなので、**変わった回数を自分で数えて**流した画素数にする。
- 止まったあとは R#23 が 0 のまま動かない。**止まった画素数**が答え
  (表 1302 / 裏 1222。直す前はどちらも 1622 だった)。
- 見た目はページ1 の見えている範囲 (`0x8000 + ((R#23 + y) % 256) * 128`) を落として
  `tools/vram2png.py` にかける。**止まる直前と止まったあとが同じ絵なら、切り替わりは
  目に見えない** (直す前は、止まる直前が真っ暗だった)。
- **`after frame` は `renderer none` では来ない。** 毎フレーム見張るつもりが1回で
  途切れる。`after time 0.01` で回すこと。**openMSX の `puts` は端末に出ない**ので、
  経過はファイルへ書き、Tcl のエラーは `catch` で拾って書き出す
  (これをやるまで「黙って止まる」理由が分からなかった)。

## ボットが自分で作った罠に48回中48回かかっていた (2026-11-08)

**面14 を敵なしで走らせたら、48回とも同じ升 (1,6)・同じフレーム (2454) で
岩に潰れた。** 敵が1人も居ないのに、である。

辿るとこういう順序だった。

```
   .O.   岩 (1,4)      1. 自機は黒ダイヤ (1,5) を割り、**その升に乗って採る**。
   .x.   黒ダイヤ(1,5)    乗っているあいだは**自機が岩の支え**になっている。
   .@.   自機 (1,6)    2. 採り終えて下へ1升。支えが外れ、岩が揺れ出す。
                       3. 45フレーム揺れて落下。割れた升 (1,5) を通り抜けて
                          自機の升へ届く。
```

ゲームの規則としては正しい。**支え判定が見るのは岩の1升下だけ**なので、
2升下に居る自機は支えていない (`supported()`、Dig Dug 準拠)。
人間なら0.75秒の揺れを見て**横へ**よける。

**ボットはよけなかった。** 経路の重み (`bot_cost`) は「岩の升 +48」と
「岩の**真下** +96」しか持っておらず、**2升下は無料**だった。
`under_falling_rock` のほうは揺れている岩を一律で安全としている
(「真下に入れば支えになる」という理屈) が、**その理屈が成り立つのは真下の1升だけ**。
しかも賢いボットの経路はそちらを見ていない (`danger_at` は記録用に残っているだけ)。

**直し方**: `rock_drops_onto()` を足して、同じ列を上へ辿り、**揺れ中/落下中の岩が
割れた升や掘った升を通って届く升**に真下と同じ罰則 (+96) を付ける。真下の1升は
除く (そこに立てば本当に支えになるので、黒ダイヤを割るのに立ち続けられる)。
面14 は敵なしで**残り1枚**まで進むようになった (そこは体温切れ)。

**一般化すると**: *避ける規則の例外を、成り立つ範囲より広く書いていた。*
「真下に立てば支えになるから揺れは安全」は正しいが、**真下でないときまで
安全に数えていた**。しかも**その形は自機が自分で作る** —— 支えの黒ダイヤを
真下から割れば、必ず岩と自分の間に割れた升が1つ挟まる。
**例外を書いたら、それが崩れる形を自分で作れないか考える。**

**測り方**: 敵を外して (`pool_tbl` の該当面を 0 にして) 走らせると**決定論になる**。
同じ升・同じフレームで死ぬので、毎フレームの `"r":[[状態,列,行],...]` を
死ぬ手前80フレームぶん並べれば順序がそのまま読める。
**敵が居るうちは21秒で敵に倒されるので、この罠は一度も見えなかった。**
**原因を1つずつ外して決定論にする**のが先。

## 「音が遅れている」と言われて音を調べた話 (2026-11-08)

**ダイナマイトを拾ったときの効果音が相当遅れている**（作者の報告、2026-11-06）。
報告の言葉どおりに音の経路を疑って、ボタンで鳴る音を openMSX で測った。
**押した次のフレームには PSG のレジスタが変わっていた。** 音は遅れていない。

遅れていたのは**拾う判定**だった。もとは「升の節点にぴったり乗ったときだけ拾う」で、
自機も拾い物も 16×16 なので、**絵が重なり始めてから節点に届くまで 15px**。
坑道は 1px/フレームなので **15フレーム ≒ 0.25秒**、重なって歩いているのに
何も起きない時間ができる。遅れて聞こえたのは、そのとおり遅れていたから。

**直し方**: **自機の中心が入った升**で判定する（`(px+8)>>4`）。重なりが半分を
越えた瞬間に拾うので 8フレーム早い。節点ではこれまでと同じ升になるので、
節点に乗って拾う分の挙動は変わらない。

```
節点で判定  py=32 で stock が増える  frame 139
中心で判定  py=24 で stock が増える  frame 131   <- 8フレーム早い
```

（面1 の出発点 [7,1] から真下の火薬 [7,2] へ下キーを押しっぱなしで歩かせて実測。
turbo R の実機BIOS。`stock` が増えた瞬間の `py` と `frame_n` を読む）

**一般化すると**: *報告された症状の名前で、調べる場所を決めてしまった。*
「音が遅れる」は**出力の遅れ**にも**引き金の遅れ**にも見えるが、
調べるべきは「鳴らせと言った時刻」のほうだった。
**「出てくるのが遅い」ときは、出口より先に入口の時刻を測る。**

## 新しい黒ダイヤを入れたときに踏んだ3つ (2026-11-08)

「手掘りでは採れない黒ダイヤ」(硬磐。`COAL_HARD`) を入れたときに、順に3つ踏んだ。
どれも**作ったその日に測って見つかった**ので、形として残しておく。

### 1. 升ごとの旗 (`cflag[]`) はもう1ビットも空いていない

`CF_HARD 0x40` として旗を足したが、**bit6 / bit7 は土の膜 (`LINK_RIGHT` /
`LINK_DOWN`) が使っている**。`game.h` の `CF_PROP 0x20` の下にそう書いてあるのに、
その行の上に新しい `#define` を足して気づかなかった。

**直し方: 旗ではなく値で持つ。** 黒ダイヤは `coal[]` に 0 / 1..11 / 255 しか
入っていないので、254 を「硬磐」に当てた。既にある判定のほとんど
(`cell_coal()` / `coal_smash()` / `coal_refill_at()`) が**そのまま正しく通る**という
おまけも付いた。**升ごとの旗を足したくなったら、まず値で持てないかを考えること。**

### 2. 「割れるまで叩く」ループが永久に回った

測る道具の側に `while (cell_coal(c, r)) { coal_hit(c, r); }` が4か所あった。
硬磐は `coal_hit()` が耐久を減らさずに戻すので、**そのまま永久に回る。**
`--sweep` が黙って返ってこなくなり、最初は「重くなった」と思って待っていた。

**「割れるまで」と書いた繰り返しは、割れないものが来たときに止まるか確かめる。**

### 3. 毎フレームの全升走査で fps が 9 落ちた

詰みの判定を「176升を見て硬磐を探す」と書いたら、Z80 機で **50.05 → 40.85 fps**。
硬磐が置かれるのは仕込んだ鉱脈の一番下だけなので、組み立てのときに控えた升
(`gapv_bi[]`、最大2つ) だけを見る形に直して 49.35 まで戻した
(代償は 0.70 fps。turbo R は 59.80 のまま)。

**毎フレーム走る処理に `for (i = 0; i < NCELL; i++)` を書いたら、前後で測ること。**

### 4. 新しい地形が岩を支えてしまい、盤面が無言で死んだ

硬磐を「ただの黒ダイヤの一種」として足したので、**岩を支える**ところまで引き継いだ。
普通の黒ダイヤならそれでよいが、硬磐はつるはしで割れず、貫けるのは落下中の岩だけなので、
真上に止まった岩は**二度と動かない**。しかもその岩が列を塞ぎ、上から落とした別の岩も
そこへ着地して割れる。作者が面14 でこれを踏み、**詰み判定も出ないまま**ゲームオーバーまで
行った。「硬磐の真上へ岩を運ぶ」は誰でも最初に試す手なのに、それが無言で盤面を殺していた。

**直し方は `supported()` に1行**（硬磐は支えない）。載った岩はその場で落ちて貫く。
代償は Z80 で 0.40 fps、turbo R は変わらない。

**新しい地形を足したら、「岩が載ったらどうなるか」を必ず試すこと。** 支える／支えないの
どちらが正しいかは、その地形を**後から壊せるか**で決まる。壊せないものが岩を支えると、
そこは盤面の墓場になる。

### 5. 試しの失敗を、まずゲームのせいにした

上の直しを入れて測ったら 36件すべて失敗で、「直っていない」と見えた。原因は試しの側で、
`rock_place()` は `rock_prop[]` を触らないので、**前の盤面の支柱を引き継いだ岩**を
置いていた（支柱つきの岩は定義どおり落ちない）。落としたら18件すべて通った。

さらに「貫いたあとも詰み判定が出る」ほうは**判定が正しかった**。鉱脈は面ごとに2本あり、
試しは盤面の岩を全部どけてから片方にだけ岩を置くので、もう一方の硬磐には岩が1つも無い。

**数字がおかしいときは、まず測定スクリプト自身を疑う**（Tcl の `after` と同じ教訓）。

## 速度の測り方

**推測で「速くなった」と言わない。** 実測の手順は次のとおり。現在の fps（turbo R と Z80 の
比較表）は [GAME_RULES.md](GAME_RULES.md) §13b にある。

1. `frame_n`（`src/main.c`）が1フレームごとに増えるので、openMSX の `debug read memory` で
   2点の値を読んで差を取る。**タイトル画面でも `frame_n` は進む**ので、体温（`temp`）が
   上がり始めたことを確かめてから数える（確かめずに測ると、タイトルの 60fps を
   「ゲーム中の fps」として報告することになる）。
2. 内訳は openMSX から `reg pc` を定期サンプリングし、リンクマップの記号へ割り当てる。
   **`static` の関数はマップに出ない**ので直前の関数に誤って集計される（実測では
   `wait_vsync` が38% ＝ 待ち時間だった）。

自機の速度も同じ要領で確かめられる（0.2秒ごとに `px` を読む）。掘削中は 0.2秒あたり 8px
= 40px/s、坑道は 12px = 60px/s。障害物で止まると 0px の区間が混ざるので、平均だけを見ると
遅く見える点に注意。

## タイトル画像を差し替えるとき

`assets/title.png` を置き換えて `make` すれば ROM に反映される（`tools/png2sc5.py` が
SCREEN 5 の16色へ落とし、`tools/ihx2rom.py` がセグメント4〜7へ入れる）。素材の条件:

- **256×212 相当**（4:3 で作る。`Makefile` の `TITLE_OPTS` で切り出しと透かし消しを指定している）
- **フラットな塗り・硬い輪郭**が16色に落としやすい。写真調の広いグラデーションは帯が出る
- **PNG（可逆）**。JPEG の圧縮ノイズは減色時に汚く出る
- **副題「〜先山丹野3時〜」は絵の中に描かない。** いまの絵は生成画像で、その部分の
  漢字が崩れていた（「先」が「光」、「野」が「墅」に見える）。`Makefile` の
  `TITLE_OPTS` の2つめの `--black` でその帯を消し、ゲーム側が 16x16 の字で描き直す
  （`kanji_subtitle()`）。**絵を差し替えたら、その帯の座標を測り直すこと。**
  色は `tools/png2sc5.py` が絵のパレットから自動で選ぶので、番号を手で直す必要はない
- 背景の黒にノイズが乗っていると減色器がパレットを何枠も食うので、`--blackfloor`（既定1）で
  暗すぎる色を黒へ寄せている

## 絵とパレットの約束

- **絵の正は `assets/` の PNG。** `make` のたびに C の配列（と ROM のセグメント）へ変換される。
  差し替えたいときは PNG を描き替えて `make` し直すだけでよい。
- **セルは 16x16 で左から順に並べる。** 順番が絵の番号になる（`Makefile` の `ART_SPR_NAMES` /
  `ART_TILE_NAMES` と対応）。透明（アルファ0）は「描かない画素」。
- **スプライトは1行に1色**（mode 2 の制約）。1行に複数色を置くと、その行で一番多い色に丸められる。
- **`tools/palette.py` と `src/main.c` の `set_game_palette()` は必ず一致させること。**
  絵の変換は前者を見て色番号を決めるので、食い違うと ROM の中だけ色が変わる。
- 坑道の上に重ねるタイル（火薬・風呂など）は**外周2pxが描かれない**（掘り跡の「薄い土の膜」を
  消さないため）。絵は内側 12x12 に収める。黒ダイヤは 16x16 全部を使う。

詳しくは [ART_PATTERNS.md](ART_PATTERNS.md)（何が何枚あって、どの状態で出るか）と
[GAMEDATA_FORMAT.md](GAMEDATA_FORMAT.md)（外部ツールとの JSON 往復）を参照。
