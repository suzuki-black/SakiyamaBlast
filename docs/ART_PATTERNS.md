# 絵とアニメーションの一覧（現状）

**キャラを描き替える前に「何枚必要か」を決めるための資料。**
いま何が何枚あって、どの状態でどれが出るかを、コードから起こしたもの。

- 絵の正: `assets/sprites.png` / `assets/tiles.png`（PNG が正。`make` で C へ変換）
- 名前の並び: `Makefile` の `ART_SPR_NAMES` / `ART_TILE_NAMES`
- 番号の定義: `src/game.h` の `PAT_*` / `src/art.h` の `TILE_*`
- 往復編集: `make gamedata` → `gamedata.json` → `make gamedata-import`（`docs/GAMEDATA_FORMAT.md`）

> **`gamedata.json` は 2026-09-01 生成のままで古い。** 「各キャラ1枚しか絵が無い」と
> 書いてあるが、いまは自機だけで17枚ある。描き替え前に `make gamedata` で作り直すこと。

## 1. スプライト（全35枚）

**16×16 / 1面1枚 / mode 2（1行1色）。** いま32面のうち **23面**を使っている
（自機1・爆弾1・岩8・敵6・かけら6・鉱車1）。**絵は35枚**。

### 自機「丹野3時」— 17枚

| 状態 | 枚数 | パターン | コマ送り |
|---|---|---|---|
| 正面 | 1 | `PAT_MINER` | **面の開始時、まだ一度も動いていない間だけ。** 以後は出ない |
| 歩き | **8**（4方向×2） | `PAT_WU1/2` `PAT_WD1/2` `PAT_WL1/2` `PAT_WR1/2` | `WALK_FRAMES` **8フレームごと**に2コマを交互。**止まっていてもコマ1で立ち姿**として使う |
| 溜めの構え | **4**（4方向） | `PAT_BRU` `PAT_BRACE`(下) `PAT_BRL` `PAT_BRR` | **1方向1枚。** 溜めの段（1〜3）では絵を変えない。段の差は**背景の汗**で出している |
| 振り下ろし | **4**（4方向） | `PAT_STU` `PAT_STD` `PAT_STL` `PAT_STR` | **1方向1枚。** 振っている `PICK_FRAMES` 18フレームずっと同じ絵。**振りの動きは背景のつるはし（3段）**で出している |

**選び方**（`player_pattern()`）:

```
まだ動いていない or 向き未定 -> 正面
振っている                   -> 振り下ろし[向き]
溜めが2段以上               -> 構え[向き]
それ以外                     -> 歩き[向き][コマ]
```

### 敵 — 11枚

| 状態 | 枚数 | パターン | コマ送り |
|---|---|---|---|
| 通常（ネズミ） | **4** | `PAT_RAT` + `PAT_RAT1`〜`+2` | **歩いた距離で位相が進む。** 1升（16px）渡るあいだに一巡 |
| よろけ | **3** | `PAT_STUN1/2/3` | 段（1〜3）で切り替え。時間で1段ずつ戻る |
| 透明化中（コウモリ） | **4** | `PAT_BAT` + `PAT_BAT1`〜`+2` | 8フレームごと。体ごとに位相をずらす |

**4種類の敵は色だけが違う。** 色は狙う升の決め方（アルゴリズム）を表す情報なので、
**状態表示に色を使ってはいけない**。4方向の描き分けは無い（どの向きでも同じ絵）。

#### うねうね動かす（2026-10-28）

**位相はフレーム数ではなく「歩いた距離」で進める**（`(en_x + en_y) >> 2 & 3`）。
速い種ほど速くうねり、岩に詰まって止まっている間はうねりも止まる。状態変数を
1バイトも増やさずに済む。**土をすり抜けている最中だけは時間で回す**——斜めに進むので
x と y が打ち消し合い（右上なら x+1 y−1）、距離では位相が進まないため。

16×16 で生き物に見せるときの勘どころ（道具は `tools/gen_enemy_anim.py`、`make enemy-anim`）:

- **絵ごと平行移動しても動いて見えない。** 身をよじったのではなく表示が揺れている
  ように見える。身をよじる＝**行ごとに違う量ずらす**こと。いまは上半身と下半身が
  逆へ寄る S 字の波を、時間とともに下ろしている。
- **一番広い行を [1,14] に詰めた。** 端まで使っていると、ずらしたぶんが画面外へ
  削れるだけでうねりが出ない。左右に1pxずつ遊びが要る（ネズミは1px細くなった）。
- **縦にはずらせない。** 下の `row_role[]` が行の役で色を当てているので、縦にずらすと
  色の帯と絵が合わなくなる。**横にしかずらさない。**
- **耳をぱたぱたさせない。** コマごとに形を変えると、うねりではなく瞬きに見える。
  耳は体のうねりに乗せるだけにした。

**透明化中はコウモリの絵に替えた。** `PAT_BAT` は絵だけあって一度も描かれて
いなかった（透明化中は淡い色のネズミだった）。羽ばたきは行の役に縛られない
（16行ぜんぶ淡色一色なので）ので、波ではなく4枚を直接描いてある。

パターン番号は **4枚が続き番号**。`enemy_draw` は RAM 実行の枠に居て表を持つ余裕が
無いので、位相から足し算だけで選べるようにしてある。

#### 行ごとに役を当てて多色にする（2026-10-11）

mode 2 は1行1色なので、**色の違いは横の帯でしか出せない**。絵の行を役で分け、
`src/enemy.c` の `row_role[]` で段ごとに並びを持っている。

| 行 | 役 | 色 |
|---|---|---|
| 耳・足 | `RL_SKIN` | 肌色（**橙だけ灰**。橙の体 `COL_RAT` は肌色とほぼ同じ色味で、肌色にすると耳も足も体に沈む） |
| 目の帯 | `RL_EYE` | 白。**絵のほうが穴**になっているので、そこが瞳として抜ける |
| 足元 | `RL_DARK` | 影 |
| 残り（体） | `RL_BODY` | **種の色**。一番広いので遠目でも種が分かる |

よろけると体が潰れて役の行が下がるため、**段ごとに表を持つ**（4段×16行＝64バイト）。
**色そのものは段で変えない**（色は種の印であって状態表示ではない）。
以前は白い帯を目より上に置いていたので、体は一色のままだった。

## 3. 絵を持たず、背景に手続きで描くもの

**ここはパターン数に数えない。** 描き替えの対象外だが、
**スプライトのコマ数を決めるときに関係する**ので載せる。

| もの | どこ | コマ数 | なぜスプライトでないか |
|---|---|---|---|
| **つるはし（振り）** | `draw_swing_fx` | **3段**（`PICK_FRAMES` 18 を3分割） | 自機のスプライトは16×16がほぼ埋まっていて、**1行1色**なので持たせる余地が無い。面を増やすと横一列8枚の制限に触れる |
| **汗（溜め）** | `draw_charge_fx` | 段（1〜3）ごと | 同上 |
| 水風呂の泡 | `draw_bath_active` | **8コマ**（上がって戻る） | 位置が固定で、面を使う価値が無い |
| 土 / 坑道 | `draw_cell_dirt` `draw_dug_cell` | — | 矩形塗り。隣が掘れているかで形が変わる |
| 黒ダイヤの耐久数字 | `draw_coal` | — | BIOS フォント |
| 得点ポップアップ | `score_popup` | — | 同上。800点以上は倍角 |
| 採掘の閃き | `take_one` → `coal_shake_tick` | 白 → 水色 → 元 | 升を塗るだけ |
| 面の開始「第 n 坑 m 番方」 | `kanji_draw` | — | 自前の16×16を18字（`docs/KANJI_FORMAT.md`） |

**溜めと振りの最中は自機が必ず静止している**ので、背景に描いて離れるときに消せる。
これが「1方向1枚で足りている」理由。

## 4. 増やすときの制約と予算

### 数の制約

| 制約 | 値 | 効くところ |
|---|---|---|
| スプライト面 | 32面中 **23面使用**（残り9面） | 同時に出せる数 |
| **VRAM のパターン** | 256枚（8×8）中 **140枚使用**。16×16 は1枚で4枚ぶん食う | **絵は残り29枚しか足せない** |
| **横一列** | **8枚まで。9枚目以降は消える** | 岩を「1行に1個」に制限している理由 |
| **1行1色** | mode 2 | 自機につるはしを持たせられない理由 |
| 色 | 512色中16色 | パレットは面ごとに差し替え可 |

### ROM の予算（**絵は専用セグメント**。窓ではない）

絵はバンク窓 0xA000 ではなく ROM の専用セグメントにある（`ART_TILE_SEG`=10 /
`ART_SPR_SEG`=11、各 8KB）。読むときだけ窓をそこへ向ける（`src/art.c`）。
**窓の空きは絵の予算と関係ない。**

| 足すもの | 1枚あたり | いま | 空き |
|---|---|---|---|
| スプライト | **48バイト**（絵32＋行ごとの色16） | 35枚 = 1680/8192 | **135枚ぶん** |
| タイル | **128バイト** | 20枚 = 2560/8192 | **44枚ぶん** |

**ROM の容量はもう制約ではない。効いてくるのは上の VRAM のほう**（残り29枚）。
「歩きを4方向×2コマ（+8枚）」「振りを3コマ（+8枚）」「構えを段ごと（+8枚）」を
全部やると 24枚で、ほぼ使い切る。

> **絵は固定領域に置かない。** 置き場の話は `CLAUDE.md` の「逃がし先は3つある」。

## 6. 描き替えの手順

```bash
make gamedata          # assets/*.png -> gamedata.json (まず作り直す)
# gamedata.json の pixels をエディタで編集、または assets/*.png を直接描き替え
make gamedata-import   # gamedata.json -> assets/*.png
make                   # PNG -> C -> ROM
```

**枚数を増やすときは `Makefile` の `ART_SPR_NAMES` に名前を足し、
`src/game.h` に `PAT_*` を足す**（並び順を一致させること）。
`ART_SPR_N` は生成側が出すので、転送漏れは起きない。
